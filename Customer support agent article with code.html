Building a Customer Support Resolution Agent That Knows When to Stop

Eight steps from system prompt to audit log, with a human always one handoff away

Most support questions follow the same few patterns: a refund request, a failed login, a billing question, a product that stopped working. Answering them in seconds instead of hours is the difference between a customer who stays and one who leaves. But an agent that can issue refunds can also make expensive mistakes, so the real design question is not how to make it helpful. It is how to make it helpful inside limits you can prove.

The Claude SDK is the brain, and the harness is the body

In this design, the Claude SDK does the thinking. It reads the customer's message, decides what information it needs, picks a tool, and writes the reply. The harness is the plain code around it. It runs the loop, sends each turn to the brain, executes the tools the brain asks for, and decides when the conversation is finished.

That split matters. The brain is good at ambiguity: understanding what a frustrated customer actually wants. The harness is good at rules: checking an amount against a cap every time, without exception. Keeping those two jobs separate means you can trust the rules even when the brain makes a judgment call you didn't expect.

Step 1: Define the system prompt with case facts

The system prompt carries the state of the current case: customer ID, order ID, the amount under discussion, and the refund cap that applies. Those facts are pinned at the top of every turn, so the model never has to reconstruct who it is talking to from the conversation history. Hooks update the block after state-changing tool calls, which keeps it honest.

Python
case = {"customer_id": "C-1042", "order_id": "88213", "amount": 24.99, "cap": 100}

system = (
    f"CASE_FACTS: {case['customer_id']} · {case['order_id']} · "
    f"${case['amount']} · cap=${case['cap']}"
)

Step 2: Define the four-tool registry

The agent gets four tools: verify_customer, lookup_order, process_refund, and escalate_to_human. Each tool description is kept to four lines: what it does, when to use it, its edge cases, and how it orders relative to its peers. That last line matters more than people expect. Telling the brain that verification must come before any refund removes a whole class of errors where the agent acts on an unverified identity.

Python
tools = [
    {"name": "verify_customer",
     "description": "Confirm identity. Always call first, before any order or refund step.",
     "input_schema": {"type": "object", "properties": {"customer_id": {"type": "string"}}, "required": ["customer_id"]}},
    {"name": "lookup_order",
     "description": "Fetch order details. Call after verify_customer succeeds.",
     "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}},
    {"name": "process_refund",
     "description": "Issue a refund. Requires a verified customer and a looked-up order.",
     "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}, "amount": {"type": "number"}}, "required": ["order_id", "amount"]}},
    {"name": "escalate_to_human",
     "description": "Hand the case to a human reviewer. Use when a call is blocked or out of scope.",
     "input_schema": {"type": "object", "properties": {"reason": {"type": "string"}, "recommended_action": {"type": "string"}}, "required": ["reason"]}},
]

Step 3: Wire the PreToolUse policy hook

This is the most important safety decision in the system. Before process_refund executes, a hook reads the requested amount and compares it to the refund cap in policy. If the amount is within the cap, the call proceeds. If it exceeds the cap, the hook blocks the call and returns a message that goes back to Claude, which can retry with adjusted arguments or escalate.

The reason to do this in code rather than in the prompt is that prompts are suggestions and hooks are guarantees. A model can misread an instruction under pressure. A comparison in code cannot.

Python
class PolicyBlock(Exception):
    pass

def pre_tool_use(name, tool_input, cap):
    if name == "process_refund" and tool_input["amount"] > cap:
        raise PolicyBlock(f"Refund ${tool_input['amount']} exceeds cap ${cap}")

def run_tools(content, cap=100):
    results = []
    for block in content:
        if block.type != "tool_use":
            continue
        try:
            pre_tool_use(block.name, block.input, cap)
            out, err = dispatch(block.name, block.input), False
        except PolicyBlock as e:
            out, err = str(e), True
        results.append({"type": "tool_result", "tool_use_id": block.id,
                        "content": str(out), "is_error": err})
    return results

Step 4: Run the agent loop on stop_reason

The loop is simple. It sends the conversation to the Claude SDK, reads the stop reason, and branches. When the stop reason is end_turn, the loop ends and the reply goes to the customer. When it is tool_use, the harness runs the requested tools through the registry, returns the results, and sends the conversation back to the brain. Nothing clever is happening here, and that is deliberate. A loop that is easy to read is easy to audit.

Python
import anthropic

client = anthropic.Anthropic()
messages = [{"role": "user", "content": "I was charged twice for order 88213."}]

while True:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        system=system,
        tools=tools,
        messages=messages,
    )
    if resp.stop_reason == "end_turn":
        break
    if resp.stop_reason == "tool_use":
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": run_tools(resp.content)})

Example 1: A refund under the cap

A customer writes: "I was charged twice for order 88213. Can I get the duplicate $24.99 back?"

The Claude SDK reads the message and asks for verification first, because the tool descriptions say to. The harness runs verify_customer, and the customer checks out. The brain then calls lookup_order and confirms the duplicate charge. It proposes process_refund for $24.99.

The PreToolUse hook reads the amount, compares it to the $100 cap, and lets the call through. The refund executes. The harness updates the case facts to show the refund is complete, and the brain writes a short reply confirming the amount and the expected timing. The loop ends on end_turn. The whole exchange is logged.

Nothing in that flow required a human, and nothing required the model to remember a rule. The cap was enforced by code.

Python
messages = [{"role": "user", "content": "I was charged twice for order 88213. Can I get the duplicate $24.99 back?"}]
# process_refund(amount=24.99) -> hook: 24.99 <= 100 -> executes -> stop_reason "end_turn"

Step 5: Add the structured escalation block

When a call is blocked, or the case is beyond what the agent should resolve, the agent pushes a structured record to the escalation queue. It includes the customer ID, the customer's intent, the partial state of the case, the blocked tool, the reason, and a recommended next action. A human reviewer can triage that in about ten seconds. Reading a full transcript to reconstruct the same context takes around five minutes. Multiply that across a queue and the economics change quickly.

Python
def escalate(customer_id, intent, partial_state, blocked_tool, reason, recommended_action):
    queue.push({
        "customer_id": customer_id,
        "intent": intent,
        "partial_state": partial_state,
        "blocked_tool": blocked_tool,
        "reason": reason,
        "recommended_action": recommended_action,
    })

Example 2: A refund over the cap

A different customer writes: "My $340 order arrived broken. I want a full refund."

Verification and lookup go the same way. The brain proposes process_refund for $340. The hook compares it to the $100 cap, blocks the call, and returns the reason to Claude.

Here is the part that is easy to get wrong. The brain may be tempted to split the refund into smaller amounts to get under the cap. The policy doesn't allow that, and the hook's block is what enforces it. So the brain takes the other path: it calls escalate_to_human with a structured record. The record says the customer's intent is a full refund for a broken item, the partial state shows the order is verified and the item is confirmed, the blocked tool was process_refund at $340, the reason is that the amount exceeds the $100 cap, and the recommended action is a manual refund review.

The customer receives a reply saying the request has gone to a specialist who will follow up. The reviewer sees the case in the queue and resolves it in about ten seconds, because everything they need is already on the record.

Python
messages = [{"role": "user", "content": "My $340 order arrived broken. I want a full refund."}]
# process_refund(amount=340) -> hook: 340 > 100 -> is_error=True in tool_result
# next turn: model calls escalate_to_human(...) instead of splitting the refund

Step 6: Wire the sentiment and confidence gates

Not every case should be resolved by the agent even when every tool call is allowed. A customer who is visibly angry, or a case where the brain's confidence in the intent is low, should go to a person. These gates sit between the brain's proposed action and its execution. They are cheap to run, and they catch cases where a technically correct resolution would still damage the relationship.

Python
def should_escalate(sentiment, confidence):
    return sentiment < -0.6 or confidence < 0.7

Step 7: Cache the system prompt for cost

The system prompt, with its tool definitions and policy context, is the same across most turns of a conversation. Caching it means the brain does not pay full processing cost for that stable prefix on every call. At support volumes, this is one of the simplest levers for keeping per-resolution cost predictable.

Python
resp = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system=[{"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}],
    tools=tools,
    messages=messages,
)

Step 8: Audit log every resolution

Every resolution, every blocked call, and every escalation is written to an audit log: what was asked, what was checked, what was done, and who or what decided. When a refund is questioned six weeks later, the log answers the question without anyone needing to remember what happened.

Python
import json, time

def audit(event, **fields):
    with open("audit.log", "a") as f:
        f.write(json.dumps({"ts": time.time(), "event": event, **fields}) + "\n")

audit("refund_executed", customer_id="C-1042", amount=24.99, decided_by="hook")

What ties it together

Read in order, the steps form a pattern. The Claude SDK is trusted to understand and propose. Code is trusted to enforce. Humans are trusted to decide the cases that fall outside the lines. Each boundary is explicit, and each one can be tested on its own.

The real lesson for anyone building agents in production is not how capable the model is. It is where you put the guarantees, and which decisions you refuse to delegate.
